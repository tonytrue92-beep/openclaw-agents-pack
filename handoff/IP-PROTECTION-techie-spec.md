# ТЗ технарю — защита IP (база знаний + характеры агентов)

**Дата:** 2026-06-12 · **Приоритет:** высокий (после TRY-блокера).
**Проблема (со слов клиента):** «просто даёшь codex установщик — и он всё
пиздит без токена». Подтверждено: шаблоны и база знаний качаются из
ПУБЛИЧНЫХ ссылок `raw.githubusercontent.com/.../templates/...`, токен в
скачивании не участвует. Плюс плейнтекст базы знаний лежит в ИСТОРИИ git —
читается даже из старых коммитов. Локальное шифрование при публичном репо
не помогает (история). Реальный фикс — приватные репо + доставка по токену.

## Что считаем ценным (это прячем)
- `openclaw-agents-pack/templates/knowledge/` — 11 выжимок методологии курса
  (кастдев, офферы, прогрев, воронки, дожим, вебинар, продуктовая линейка…).
  ЭТО ГЛАВНОЕ — по сути платный контент курса.
- `templates/<agent>/` — характеры агентов: SOUL/LEARNING/skills.
- Скрипты установщиков — НЕ секрет (bash-сантехника), но уедут в private заодно.

## Целевая схема: приватные репо + token-gated доставка

### Эндпоинт (на твоём сервере, рядом с Prodamus-webhook и аналитикой)
```
GET /ip/templates?tier=<VIP|STD>&token=<course-token>
GET /ip/agent?id=<tech|marketer|...>&token=<course-token>
GET /ip/knowledge?token=<course-token>     # только VIP
```
Логика:
1. Проверить course-token локально по Ed25519-pubkey (код у тебя уже есть из
   верификации токенов) — подпись валидна И tier разрешает запрошенное.
2. Если ок — отдать tar.gz нужных файлов (стримом). Если нет — 403, пустота.
3. KB отдавать ТОЛЬКО для VIP. STD — только свои 3 агента. SUB — ничего.
4. Лог: token_hash (sha256 полного токена) + что запросили — для трассировки.

### GitHub
- Перевести `openclaw-factory`, `openclaw-agents-pack`, `openclaw-test-drive`
  в **private** (это прячет и историю — главное).
- Сам установщик-скрипт держать так, чтобы команда из бота работала:
  вариант А — отдавать demo-install.sh тоже через твой эндпоинт
  (`GET /ip/installer?token=...`); вариант Б — тонкий ПУБЛИЧНЫЙ репо-лаунчер
  только со скриптом-загрузчиком (без IP), который тянет всё остальное по токену.
  Рекомендация: вариант А (одна точка, всё за токеном).

### Команда в боте (после флипа)
Бот выдаёт команду, которая несёт токен в загрузке установщика, например:
```
COURSE_TOKEN=<token> bash <(curl -fsSL "https://<твой-домен>/ip/installer?token=<token>")
```
Установщик дальше дергает /ip/* с тем же токеном (из env/кэша).

## Последовательность переключения (чтобы НЕ уронить установки)
1. Ты поднимаешь эндпоинт /ip/* и проверяешь его токеном вручную (curl).
2. Присылаешь мне базовый URL. Я завожу его в установщики ОДНОЙ переменной
   (`IP_BASE`) — на ветке, со smoke-проверкой, релиз кандидат.
3. На тестовом токене прогоняем полную установку с нового источника.
4. Только когда зелено — ты меняешь команду в боте и переводишь репо в private.
5. Я выпускаю финальный релиз. Откат — вернуть IP_BASE на старое + public.

## Доп. меры
- **Ротация KB после флипа:** старый плейнтекст мог быть уже скачан. Имеет
  смысл слегка обновить/переписать выжимки, чтобы утёкшая версия устарела.
- **Watermark уже есть** (в IDENTITY.md зашит хэш токена покупателя) — слитый
  УСТАНОВЛЕННЫЙ воркспейс отслеживается. Доставку это не закрывает, но
  деанонит источник слива.
- **Ревокация:** раз доставка по токену — отозванный токен (прошлый поток,
  возвраты) автоматически теряет доступ к IP. Свяжи с задачей отзыва токенов.

## Если сервер не скоро — промежуточный вариант (слабее)
Private-репо + один fine-grained read-only GitHub PAT (contents:read на 3 репо),
бот вшивает его в команду как `Authorization`-заголовок. Публика/codex без
команды → 404 (и история скрыта). Минус: PAT общий — при утечке ротируешь у
всех. Это та же модель «платный имеет доступ, публика нет», что ты уже принял.
