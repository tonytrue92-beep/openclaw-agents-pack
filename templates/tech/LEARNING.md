## Предзаполненные правила (из чужого опыта)

### 1. Бэкап ДО фикса, не после
- `[CORRECTION]` Запустил `openclaw doctor --fix` без бэкапа — он
  переписал конфиг, откатить было нечем
- `[CORRECT]` Перед любой изменяющей командой — бэкап конфига/состояния.
  Только потом фикс.
- `[RULE]` [safety] Нет бэкапа — нет рискованного действия.

### 2. Сначала логи, потом гипотеза
- `[CORRECTION]` Начал «чинить» по догадке не глядя в логи — лечил
  не ту проблему, потратил время
- `[CORRECT]` Сначала живое состояние: status, logs, config, health.
  Гипотеза строится на фактах, не на догадке.
- `[RULE]` [diagnostics] От живого состояния, не от теории.

### 3. Наименьший обратимый фикс
- `[CORRECTION]` Чтобы пофиксить одну ошибку — переписал полконфига,
  добавил новых проблем
- `[CORRECT]` Минимальное изменение которое решает проблему. Большие
  рефакторы — отдельно и с подтверждением.
- `[RULE]` [fix] Smallest safe change. Не чини то что не сломано.

### 4. Провайдер вернул HTML — это его сбой
- `[CORRECTION]` Провайдер вместо JSON вернул HTML-страницу ошибки,
  попытался это распарсить как ответ — получил мусор
- `[CORRECT]` HTML/CSS/JS вместо ожидаемых данных = сбой провайдера
  (rate limit / даун / блок). Не контент ответа.
- `[RULE]` [provider] Неструктурный ответ от API — апстрим-сбой, не данные.

### 5. Проверка после КАЖДОГО изменения
- `[CORRECTION]` Сделал 3 изменения подряд, в конце что-то сломалось —
  не понял какое именно
- `[CORRECT]` После каждого изменения — проверка. Тогда виновник
  очевиден сразу.
- `[RULE]` [verify] Одно изменение → одна проверка.
