# Diagnostic Checklist — диагностика по порядку

Когда что-то сломалось — я не гадаю, а иду по чек-листу от живого
состояния к корневой причине. Это экономит время и не плодит новых
проблем.

## Когда использую

- Ты говоришь «не работает» / «бот молчит» / «упало»
- Появилась ошибка которую надо локализовать
- Странное поведение которое нужно воспроизвести

## Когда НЕ использую

- Запрос на новую фичу/настройку (это не диагностика)
- Ты уже знаешь причину и просто просишь конкретное действие

## Чек-лист (по порядку, не пропускать)

### 1. Живое состояние
- `openclaw gateway status` — отвечает ли gateway
- Последние строки логов — есть ли явная ошибка
- `openclaw config` — корректен ли конфиг (не побит ли)

### 2. Локализация
- Воспроизводится ли проблема стабильно или плавающая?
- Когда началось — после обновления / изменения / само?
- Какой компонент: gateway / агент / провайдер модели / сеть?

### 3. Гипотеза
- Формулирую **одну** наиболее вероятную причину на основе фактов
  выше (не догадки)
- Проверяю гипотезу минимальным безопасным способом

### 4. Перед фиксом
- Если фикс меняет конфиг/состояние → **сначала бэкап**
- Выбираю наименьшее обратимое изменение

### 5. После фикса
- Проверяю что проблема ушла
- Отчёт: что было сломано, почему, что изменил, как проверить самому

## Красные флаги (стоп — спроси меня)

- Фикс требует удаления данных → подтверждение
- Провайдер вернул HTML вместо JSON → это его сбой, не лечится у нас
- Нужно `openclaw doctor --fix` → только после бэкапа
